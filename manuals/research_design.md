# 研究设计（v2.0，2026-09-29 修订：以工作片段为分析单位）

## 1. 问题与定位

越来越多的研究与管理实践以版本库为依据，判断 AI 辅助开发做了什么、按什么顺序、花了多久、AI 贡献多少，分析单位通常是提交或登记的任务。但在真实的 agent 开发中，工作与提交并不一一对应。常见情况包括：

- 客户口头提出的小改动不单独提交，随后续大版本一起进入版本库；
- 两个相关任务一起开发、一起测试、一起提交；
- 需求文件先写好，没有立即纳入版本库，开发完成后与代码一起提交；
- 写过的代码被覆盖或撤销，始终没有进入版本库。

**核心问题**：开发者与 agent 实际完成的工作，在 Git 与任务书中是怎样被表示的？哪些工作被合并、拆分、压平顺序或完全缺失？只看版本库的研究与管理判断会因此错在哪里、错多少？

**定位**：挖掘软件仓库（MSR）的效度研究，对象是智能体辅助开发。已有工作指出了 Git 数据的一般陷阱 [Bird, Kalliamvakou]。本文关注 agent 工作流特有的机制：工作区与版本库分离、agent 高频迭代编辑、计划文件与代码同步演化、人机交替决策。

**研究类型**：单企业、两系统的混合方法案例研究。
- 自动映射覆盖全部工作片段；
- 人工分类覆盖分层样本，经独立盲评检验一致性；
- 最后由企业方做成员核查。

## 2. 分析单位与数据流

**工作片段（episode）**：会话中开发者的一次请求，加上 agent 随后完成的全部动作，直到下一次请求为止。片段从会话侧定义，**不依赖 Git 或任务书是否登记过这项工作**。边界细则见 `notes/decisions.md` D4。

数据流：

```text
客户问题清单（部分可见）
        ↓
会话中的请求 ──→ 工作片段 ──→ 编辑（按内容归属）──→ 提交 ──→ 版本库视图
                      └──────→ 任务书写入 / 打勾 ──→ 任务书视图
```

以前以登记任务为单位的测量（R0，`doc/v2.0/results/r0_summary.md`）降为中间层。它以 Git 与任务书已经登记的工作为起点，只能说明规范流程内部的一致性，不能说明版本库遗漏了什么。

## 3. 研究问题

- **RQ1 映射模式**：工作片段映射到 Git 有哪些模式（一对一、合并、拆分、随他项提交、顺序压平、缺失等），各占多大比例？
- **RQ2 成因**：哪些特征与各模式相关？例如请求规模、是否转述客户口头需求、是否登记在任务书、任务间的关联、调试返工。
- **RQ3 后果**：以提交或登记任务为单位的常见度量（工作量、顺序、耗时、AI 贡献）会因这些模式产生多大偏差？
- **RQ4 方法可靠性**：自动映射与人工判定的吻合度；人工分类的独立一致性。

## 5. 方法

**5.1 片段提取（自动，S01）**：按 D4 切分片段，提取特征。特征包括规模、任务号与任务书引用、客户转述线索、是否改代码、是否提交或部署。

**5.2 编辑归属（自动，D3）**：只用编辑前文件中原本没有的新写入行，在后续提交的新增行中匹配，覆盖 ≥ 50% 即归属该提交；否则按原因记为未进入版本库。时间规则作为对照口径。

**5.3 片段—提交映射与候选模式（自动，S02）**：由编辑归属得到片段与提交的多对多关系，按 D5 给出候选模式（可多标签），并标注任务书层信息。

**5.4 人工分类（S03–S05）**：
- 按候选模式分层抽样约 50 个片段，其中 10 个试编、40 个正式；
- 每个片段一页证据包；
- 作者依据编码手册判定模式与成因，手册设开放类以发现未预料的模式；
- 王从正式组中盲评约 20 个，报告 Cohen's κ；
- 用人工结果检验自动候选模式的准确率。

**5.5 上游追踪（S06）**：从客户问题清单抽样，追踪需求 → 片段 → 提交。

**5.6 偏差估计（S07）**：用人工核验后的模式比例，估计以提交为单位的度量偏差；在 SYS_C 上复现。

**5.7 成员核查（S08）**：请项目负责人审阅分类与典型例子。

## 7. 贡献（预期）

1. 一套有实证依据的“真实工作 → 版本库”映射模式分类；
2. 两个工业系统上各模式的比例与成因；
3. 对仅用版本库的研究与管理度量的偏差估计；
4. 可复用的会话—Git 对齐方法（按内容归属编辑）。

## 8. 有效性威胁（提纲）

- 单企业，团队有任务书与任务号纪律，其他团队的映射模式比例可能不同；
- 部分编辑没有保存写入内容（SYS_A 约 37%，SYS_C 约 68%），无法按内容归属；早期会话有补写时间戳，由插值替代；
- 客户口头需求只能通过开发者在会话中的转述观察到；
- 片段边界是操作性定义，会影响合并、拆分的判定（S02 做敏感性分析）；
- 作者参与了前期探索（v1.x），可能影响分类预期，由独立盲评和成员核查缓解。

## 9. 与前期探索的关系

- v1.x 在少量家族上观察到：Git 时间晚于实际决策；粒度改变分类结论。
- R0 以登记任务为单位，发现规范流程内部顺序基本一致；但相当一部分编辑进入不带任务号的提交或未进入版本库（去重后的比例由 S02 重算）。

两者都作为本设计的动机，不作为结论引用。
