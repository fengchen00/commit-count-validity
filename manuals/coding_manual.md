# 编码手册：工作片段如何进入版本库（v2.6，冻结版）

> 适用：S03 试编、S04 正式编码、S05 独立盲评。编码对象是**工作片段**，定义见 `notes/decisions.md` D4：开发者发出一条消息，到同一会话中下一条消息之前，agent 所做的全部工作。
> 编码表：随材料发给你的 xlsx 录入表（"录入"工作表），字段与本手册第 5 节一一对应；受限字段有下拉，多值字段用英文分号分隔。
> 本版为 2026-10-01 冻结版（D29）。正式编码期间只作澄清性修订，不改判据；有疑问见第 6 节的问答通道。

## 1 为什么编码，看什么

研究问题是：真实的 agent 辅助开发中，一次工作（片段）以什么方式进入版本库，又为什么是这种方式。只看 Git 的研究默认"一次提交对应一件事"。但研究团队在阅读本案例的会话记录与自身的开发经验中观察到三种常见情况，与这个默认不符。它们是本手册初始模式的依据：

1. 口述的极小修改（如改一句文字）不单独提交，而是跟着之后一个大版本一起进入版本库。
2. 两个上下关联的任务一起开发、一起测试、一起提交。
3. 先写需求文件但不立即提交，开发完成后与代码一起提交。

编码时请根据证据包中的**事实**判断，不要依据自动候选（作者版证据包末尾的附节只供对照；盲评版没有）。证据包各节：

- 第 1 节：请求原文与前后消息。
- 第 2 节：编辑、命令、提问的时间线。
- 第 3 节：与本片段内容重合的提交、只能按时间推测的候选提交、片段期间的全部提交。
- 第 4 节：相关任务书。

## 2 主模式与次模式

每个片段填**一个主模式**，另可填若干**次模式**。主模式描述片段中**大部分新增内容**（看第 3.1 节的重合行数）进入版本库的方式；其余同时成立的写入次模式。

### 判定顺序

依次回答下面的问题，第一个"是"即为主模式的候选；然后看后面的问题是否也成立，成立的写入次模式。

1. 片段有没有改代码？没有，填 **N0**，结束。
2. 片段的代码改动有没有新增内容（而不只是重写已有内容）？没有，填 **N1**，结束。
3. 证据是否足以判断去向？第 2.1 节大量"无写入内容"、没有检查点差分、第 3.1 节为空，且第 3.2、3.3 节也无法确认时，填 **U**，并在"缺什么"中写明。
4. 新增内容是否全部没有进入版本库？是，填 **A9**。
5. 新增内容进入了几个提交？这些提交里还有没有别的片段的内容？据此在 A1–A7 中选主模式（见下）。
6. 是否另有一部分新增内容没有进入版本库？是，加次模式 **A8**。
7. 是否写了从未进入版本库的文件？是，加次模式 **A10**。
8. 以上都不贴切，填 **X** 并描述。

### 多个模式同时成立时的主模式规则

- 按重合行数：大部分新增内容所在的提交决定主模式。
- 行数相当时，按这个优先级取主模式：A9 > A6 > A3 > A2 > A7 > A5 > A4 > A1。越靠前，越偏离"一件事一次提交"。A6 与 A2 同时成立时同样适用：取 A6，A2 写入次模式。
- A4 与 A5 可以同时出现：大部分行数进入逐条任务提交、少量进入修复或无标签提交时，主模式 A4，次模式 A5；反之主模式 A5。

### 通用约定

- **什么算"改了代码"**：只算工作区内的源码、配置、脚本。`.txt`、`.tmp`、日志、图片、办公文档、压缩包、备份文件，以及工作区外的文件，都不算代码；只改这些文件的片段填 N0，在备注中说明。
- **子代理**：子代理的编辑属于启动它的片段。子代理在上一片段写好、本片段才提交的内容，仍属于上一片段；本片段只因提交了这些内容而与之同处一个提交时，本片段不算 A2。
- **检查点差分**：只统计本片段编辑过的文件。某文件在差分表中显示"—"，只表示检查点里没有看到该文件的差异；检查点会漏记，"—"既不是未提交的证据，也不是"无新增内容"（N1）的证据。该文件的去向按逐次编辑判断，逐次编辑也无写入内容时，按 U 的规则处理。
- **`git add` 与提交标题**：终端中 `git add` 列出的文件名加上提交标题，可以作为去向的辅助证据，置信度最高填 2；只有这类证据时，不填 U。
- **一次性运维操作**（直接在服务器上改数据库、配置，本就不该进入版本库）：只有这类改动的片段填 X，备注写"运维"；与代码改动并存时按代码判主模式，成因加 C9。

### 模式定义

每个模式给出定义、判据、边界，以及正例和反例（均为抽象化的示例）。

#### A1 一对一
- **定义**：片段的新增内容进入且只进入一个提交，该提交不含其他片段的内容。
- **判据**：第 3.1 节只有一个提交，且"该提交还含以下片段的内容"为"无"。
- **边界**：提交里还有开发者手动改的零星内容、看不出来源的，不影响判断。同一提交还含本片段并入的接续消息的工作，仍算一对一。
- **正例**：开发者要求修一个显示问题；agent 改了两个文件并提交一次；该提交只含这两处改动。
- **反例**：agent 改完后，同一提交还包含同会话上一个片段的改动。这是 A2，不是 A1。

#### A2 合并-同会话
- **定义**：片段的新增内容与**同一会话**中其他片段的内容进入同一个提交。
- **判据**：第 3.1 节某提交的"还含以下片段"中出现"同会话"的片段。
- **边界**：两个片段属于同一件事（后一个是对前一个的追加修改）时，仍是 A2；成因填 C3 或 C2。
- **正例**：开发者先要求调整页面间距，又要求改一处措辞；agent 两次都没提交，第三条消息后一次提交全部改动。这对应作者提出的第 1、2 种情况。
- **反例**：两个片段各自有独立提交，只是时间相近。这是两个 A1。

#### A3 合并-跨会话
- **定义**：片段的新增内容与**其他会话**的片段内容进入同一个提交。
- **判据**：第 3.1 节某提交的"还含以下片段"中出现"其他会话"的片段。
- **边界**：常见于开发者隔一段时间做一次"快照"或"版本"提交（提交时间距片段结束往往以小时或天计）。
- **正例**：某天的几个会话都没提交，两天后一次"验收版快照"提交收进了这些会话的全部改动。
- **反例**：另一个会话后来改了同一文件并单独提交，但本片段的内容早已单独提交过。这是 A1。

#### A4 拆分-逐条任务
- **定义**：片段的新增内容分别进入 ≥ 2 个提交，每个提交对应任务书中的一条不同任务。
- **判据**：第 3.1 节有多个【任务】提交，任务号互不相同；第 4 节能看到这些任务。
- **边界**：这是"一条任务一次提交"规范要求的正常结果，不是异常。
- **正例**：开发者说"继续执行某里程碑"；agent 依次完成 T1–T4，每完成一条提交一次。
- **反例**：多个提交带的是同一个任务号，或夹着修复、无标签提交。这是 A5。

#### A5 拆分-非逐条
- **定义**：片段的新增内容进入 ≥ 2 个提交，且不是按任务书逐条提交。
- **判据**：第 3.1 节有多个提交，其中有同一任务号重复出现，或有【修复】【热修】【无标签】提交。
- **边界**：是否属于返工，由成因编码回答（C3），模式本身不含这个判断。
- **正例**：开发者要求修一个导出问题；agent 提交一次后发现漏了一处，再提交一次"修复"。
- **反例**：多个提交各对应不同任务号。这是 A4。

#### A6 随他项提交
- **定义**：片段的新增内容进入的提交，其说明指向另一件与本片段请求**无关**的任务或版本。本片段的工作在版本库中没有自己的记录。
- **判据**：第 3.1 节提交的标题或任务号，与第 1 节请求所说的事、第 4 节的里程碑都对不上；从请求看，也不是同一件事的一部分。
- **边界**：
  - 提交指向的任务与请求**相关**（同一功能、上下游任务），不算 A6，填 A2 或 A3，成因填 C2。
  - 提交是无标签的"快照"或"版本"提交，填 A3 或 A2，不填 A6。
  - agent 在本片段中自行扩展了工作（改了请求没提到的文件或功能），扩展部分进入了与请求无关的提交：不据此填 A6。A6 只看请求所要的工作去了哪里；扩展部分的去向写入备注，成因加 C4。
- **正例**：开发者口头要求改一句提示文字；这处改动出现在一个标题为另一个里程碑某任务的提交里。这对应作者提出的第 1 种情况。
- **反例**：请求说"继续做某里程碑"，提交是该里程碑的任务提交。这是 A4 或 A1。

#### A7 顺序压平
- **定义**：片段先写需求或任务书，后改代码，两者在同一个提交中进入版本库。版本库中看不出"先计划、后实现"的顺序。
- **判据**：第 2.1 节任务书或文档的首次编辑早于代码；第 3.1 节同一提交同时包含两者。
- **边界**：需求文件在本片段之前已写好但未提交，本片段写代码后一起提交，同样是 A7，在备注中写明需求文件的写入时间。
- **正例**：agent 先新建某里程碑的任务书，接着实现 T1，然后把任务书和代码一次提交。这对应作者提出的第 3 种情况。
- **反例**：任务书先单独提交，代码后来另行提交。这不是 A7。

#### A8 部分未提交（只作次模式）
- **定义**：片段有一部分新增内容进入了版本库，另一部分没有。
- **判据**：第 2.1 节有"未进入提交"或"此后该文件无提交"，且检查点差分也显示未进入。没有检查点差分时，可只凭逐次编辑判断，置信度最高填 2。
- **边界**：agent 在同一片段中先写后又改掉的中间内容，不算未提交；被**后续片段**覆盖、因而没进入提交的内容，同样不算 A8（它在后续片段的去向中体现）。有检查点差分时，以差分为准。
- **中间版本**：同一文件在本片段内被多次编辑，只有较早的版本显示"未进入提交"、最后一次编辑的内容已进入提交时，视为中间版本，不填 A8。只有该文件最终内容（最后一次编辑或检查点差分）中有一部分没有进入任何提交，才填 A8。
- **正例**：agent 改了三个文件，其中一个文件的改动后来被撤销，没有出现在任何提交中。
- **反例**：逐次编辑显示"未进入提交"，但检查点差分显示最终内容已进入提交。这是 agent 自己覆盖的中间版本，不填 A8。

#### A9 缺失
- **定义**：片段有新增内容，但全部没有进入版本库。
- **判据**：第 3.1 节为空；第 2.1 节的内容去向为"未进入提交""此后该文件无提交"或"文件从未进入版本库"；检查点差分（如有）同样没有进入。
- **边界**：
  - 全部未提交内容都是"此后该文件无提交"，且片段接近观察窗口末尾时，在备注中写"窗口末"。这类可能只是还没来得及提交。
  - 内容只是临时脚本（文件从未进入版本库），主模式按脚本所改的业务文件判断；看不到业务文件的去向时填 U；只有脚本、没有业务文件改动时填 X 并说明。
  - 判断脚本是否改了业务文件：看终端命令与后续消息（如脚本运行后报告"已替换 N 处"、开发者随后验收页面效果）。有这类迹象、但编辑记录里看不到业务文件时，填 U，缺什么一栏写"脚本改动的业务文件不在编辑记录中"。
  - 可见证据须覆盖大部分新增内容才填 A9；大部分编辑"无写入内容"、只有少数能确认未入库时，填 U，次模式加 A8。
- **正例**：开发者要求试一个方案；agent 改了代码；下一条消息开发者说"算了，恢复"，改动从未提交。
- **反例**：内容无写入记录，也没有检查点差分，无法确认去向。这是 U，不是 A9。

#### A10 含未跟踪文件（只作次模式）
- **定义**：片段写了从未进入版本库的文件，如临时脚本、本地配置、被忽略的输出。
- **判据**：第 2.1 节有"文件从未进入版本库"，且文件在工作区内。
- **边界**：如果该文件本应提交却遗漏（如新功能的源文件），在备注中说明，并考虑主模式 A9 或 A8。工作区外的文件不算 A10。N0 片段写了从未入库的任务书或文档，不标 A10，在备注中说明。
- **正例**：agent 为批量修改文案临时写了一个脚本，用完未提交。
- **反例**：新文件后来进入了提交。这不是 A10。

#### N0 无代码
- **定义**：片段没有代码编辑（讨论、查询、部署、只改文档或任务书）。
- **正例**：开发者问"现在是纯静态的吗，如何部署"，agent 只回答并执行了部署命令。
- **反例**：只改了任务书，但同一片段也改了一行代码。这不是 N0。

#### N1 无新增内容
- **定义**：片段改了代码，但写入的内容在上一版本中都已存在（例如恢复、格式化、重写成同样内容）。
- **正例**：开发者要求撤销刚才的改动，agent 把文件恢复成上一个提交的样子。
- **反例**：恢复后又加了新逻辑。这不是 N1。

#### U 证据不足
- **定义**：现有证据无法判断片段内容的去向。
- **判据**：编辑大多"无写入内容"，没有检查点差分，第 3.1 节为空或只覆盖一小部分；第 3.2 节只有按时间推测的候选。
- **要求**：在"缺什么"一栏写明缺的证据（如"看不到这些文件的写入内容""推测的候选提交标题与请求无关，无法确认"）。
- **可见部分**：主模式填 U 时，能确认的那部分内容的去向仍可写进次模式（如可见部分进入同会话合并提交，次模式填 A2），并在备注中说明只覆盖可见部分。
- **正例**：片段改了十几个页面文件，全部"无写入内容"，也没有检查点差分，只有一个两天后的候选提交。
- **反例**：虽然很多编辑无写入内容，但检查点差分显示最终内容进入了某提交。可以判断，不填 U。

#### X 其他（请描述）
- **用途**：发现手册没有预料到的方式。只要 A1–A10、N0、N1、U 都不贴切，就填 X，并在备注中用一两句话描述：内容去了哪里、为什么现有模式都不合适。
- **要求**：不要为了避免用 X 而勉强套用其他模式。试编和正式编码中出现的 X 会汇总讨论，决定是否单列为新模式。

## 3 成因线索（次要编码，可多填）

回答"为什么是这种进入方式"。只填有证据支持的；依据写在备注中，例如"请求中写'客户说……'"。

| 代码 | 成因线索 | 常见证据 |
|---|---|---|
| C1 | 客户口头需求转述 | 请求中转述客户、甲方的意见或原话 |
| C2 | 相关任务一起做 | 请求或前后消息涉及上下游任务、同一功能的多个部分 |
| C3 | 调试或返工 | 请求指出错误、要求修正上一步；同一件事多次提交 |
| C4 | agent 自行扩展范围 | agent 改了请求未提及的文件或功能 |
| C5 | 批量或快照提交习惯 | 提交标题为快照、版本、阶段性；距片段结束较久 |
| C6 | 任务书流程 | 按任务书逐条执行、逐条提交 |
| C7 | 需求先写后提交 | 需求或任务书先写好未提交，后与代码一起提交 |
| C8 | 临时或辅助文件 | 脚本、测试数据、本地配置 |
| C9 | 上线或部署驱动 | 提交紧接在部署命令前后，或请求要求"更新线上" |
| C10 | 中断或未完成 | 开发者叫停、换方向，或会话中断 |
| C11 | 小改动滞留工作区 | 小改动长期未提交，后来被无关提交顺带收入（常与 A6、A3 同现） |
| CX | 其他（请描述） | |

## 4 置信度与证据充分性

- **置信度**：1 = 猜测（证据只有时间接近）；2 = 较有把握（有内容重合，但有一部分看不到）；3 = 证据明确（内容重合覆盖大部分改动，前后消息也一致）。
- **证据是否充分**：Y 或 N。填 N 时，"缺什么"必须填写。

## 6 纪律

- 独立编码：编码完成前不与其他编码人讨论具体片段；不知道、也不要打听其他编码人是谁。
- 只看证据包；需要打开原始数据才能判断时，填 `evidence_sufficient = N`，并写明需要什么。
- 证据包含商业信息，不外传、不截图、不复制到其他地方；完成后删除本地副本。
- **问答通道（代替试编）**：先做所编材料的前 5 条；对手册条文有疑问，当天通过微信问作者。作者只解释条文的含义，不回答某个片段"应该填什么"。问答由作者记录并在手册修订记录中汇总；若澄清改变了你此前的判断，可回头改前面的条目。
- **分歧处理**：两名编码人对同一材料的判断不一致时，由不参与编码的裁决人裁定；裁决人看不到答案来自谁。编码人之间不协商。
- **不要为了"看起来一致"而迁就**：拿不准就按手册填 U 或低置信度，这些正是研究要统计的量。

## 7 片段—提交对级盲评（D26-1，独立编码人单独完成）

这是与第 2 节模式编码不同的任务：不判模式，只判**一个片段与一个提交之间的内容关系**。用于独立检验对齐方法（3.4 节）与按时间归属基线的判定。

- **材料**：`任务05_对级盲评/证据包/P001.md … P072.md`，每份一对。上半是片段（请求、代码编辑列表及其写入内容、检查点差分），下半是提交（时间、标题、改动文件、在片段所改代码文件上的差异）。★ 标出片段所改文件中该提交也改了的文件。**证据包不说明这一对是哪种方法给出的，也不给自动判定；编码人不得查看 `key.csv`。**
- **问题**：这个片段在该提交所改文件上写入的内容，是否进入了该提交？
- **答案**（`answer` 列）：
  - `Y` 是：片段在 ★ 文件上**可见的**写入内容（编辑内容或检查点差分中的行）出现在该提交的差异 `+` 行中，且这些行是该提交对 ★ 文件 `+` 行的主要部分。**以该提交在 ★ 文件上的 `+` 行为分母**：片段还写了别的东西、进了别的提交或别的文件，不影响 Y。
  - `P` 部分：该提交在 ★ 文件上的 `+` 行只有一部分来自片段的可见写入（其余 `+` 行不是片段写的），或片段在 ★ 文件上的可见写入只有少数行进入、多数行在 `+` 行中找不到。
  - `N` 否：该提交对 ★ 文件的改动不是这个片段写的：片段在**全部** ★ 文件上都有可比的内容，且都不在 `+` 行中（内容对不上、以上下文行或 `−` 行出现、或改动方向相反）。
  - `U` 无法判断：片段在 ★ 文件上有编辑在导出中没有写入内容、也没有检查点行，而可见部分又不足以判 Y/P（例如可见的几行不在 `+` 行中，但另有无内容的 ★ 编辑，其内容可能就是 `+` 行）；或差异被截断、写入内容被截断而可比的行不在显示范围内。
- **判断依据的顺序**：写入内容的行是否逐字（去首尾空白）出现在差异的 `+` 行 → 检查点差分的行是否出现在 `+` 行 → 差异内容与请求描述的任务是否对得上（只作 Y/P 与 N 之间的辅助，**不能单独给 Y 或 P**）。**不要按时间先后推断**：片段之后的下一个提交未必含片段的内容。
- **检查点差分的行视同写入内容**：导出无写入内容时，检查点差分列出的行就是片段写入的内容，与编辑写入内容同等对待；只有编辑内容、没有检查点行，或只有检查点行、没有编辑内容，都可据以判 Y/P/N。
- **上下文行与 `−` 行都不算进入**：片段的写入行在差异中以上下文行（无 `+`/`−` 前缀）或 `−` 行出现，说明这些行在该提交之前就已在版本库中，即进入了更早的提交，不算进入本提交；本提交把同样的行删了再加回（如编码转换、整文件重写）也不算进入。若片段在全部 ★ 文件上的可比内容都是这种情形，答 `N`；若另有无内容的 ★ 编辑，按 `U` 条处理。
- **看不见就答 U**：片段在 ★ 文件上既无写入内容也无检查点行，或差异被截断、写入内容被截断而可比的行不在显示范围内，或证据包标"另 N 个重叠文件差异未显示""有写入内容，包中未显示"而可见部分不足以判定，答 `U`，不凭请求与差异"吻合"给 Y 或 P；`U` 不是错误答案，它正是本任务要统计的量。
- **样板行不算证据**：只在声明、导入、命名空间、花括号、空行、常见固定写法（如 `return this;`、日志模板）上对得上，不足以判 Y/P；要有带任务语义的行（函数体、字段名、文案、条件）逐字对上。
- **多个 ★ 文件时先逐文件判、再合并**：每个 ★ 文件按上述条各判一次（Y/P/N/U），合并规则：全 Y → `Y`；有 Y 也有 N → `P`；有 Y 无 N、有 U → `P`（`note` 写清哪些文件 U）；全 N → `N`；无 Y 且有 U → `U`。删除类改动条也按文件适用。
- **删除类改动（唯一可凭请求判断的情形）**：片段在 ★ 文件上无写入内容、无检查点行，且该提交对该文件的差异**只有** `−` 行，请求又**点名**要求删除这些内容（请求文字能对上被删的函数名、字段名或文案原文；"清理""精简""去掉多余的"这类泛指不算）时，可给该文件 `Y` 并在 `note` 写"删除"；差异中同时有 `+` 行时不适用本条。删除类编辑导出的"写入内容"往往只是被删行两侧幸存的邻行，与 `+` 行对上不算证据，按无内容处理。
- **`confidence`**：1 低 / 2 中 / 3 高。**`note`**：写据以判断的行或文件；`U` 时写缺什么。
- **纪律**：与第 6 节相同；每对独立判断，不回头改已判的对以求一致。
