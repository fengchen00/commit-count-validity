# 编码手册补充：公开语料（SWE-chat，Claude Code）上的模式编码（v1.0，冻结版）

> 适用：任务 06 公开语料编码（S27，D38）。与《编码手册》v2.6 第 2–6 节**一起**使用：判据以 v2.6 为准，本补充只说明公开语料与本文案例的差异、证据包各节的对应关系，以及几条 v2.6 没有预料到的情形。本补充在抽样前冻结；编码期间只作澄清性修订，不改判据。

## 0 这批材料是什么

- 语料是公开数据集 SWE-chat 中五个开源仓库（osabio、rhea-project、rudel、duckdb-data-agent、ado-git-repo-insights）的 Claude Code 会话转录，加上各仓库公开 Git 历史的完整镜像。**不是**本文案例的那家公司；会话多为英文，代码为开源代码，没有保密要求，但仍请不要把材料上传到在线工具。
- 编码对象仍是**工作片段**：开发者发出一条消息，到同一会话中下一条消息之前，智能体所做的全部工作。片段 ID 形如 `SW-osa-1a2b3c4d-07`：仓库缩写、会话 ID 末 8 位、会话内第几条开发者消息。
- 要回答的问题与 v2.6 相同：这个片段新写入的代码以什么方式进入了版本库（主模式、次模式、成因、置信度、证据是否充分）。
- 你看不到、也不需要知道：这个片段属于哪一类会话、自动判定给了什么模式。证据包只有事实记录。

## 1 证据包各节与 v2.6 的对应

| 本证据包 | v2.6 手册所指 | 差异 |

| 第 1 节 请求与上下文（上一条 / 本条 / 下一条开发者消息原文；本会话全部开发者消息的时间与摘要；智能体对本条的最后回复摘要） | 第 1 节 | 多了"会话内全部消息摘要"，用来判断前后片段是否同一件事（A2）与提交指令在哪条消息里 |
| 第 2.1 节 编辑（按文件） | 第 2.1 节 | **没有检查点差分一栏**（该语料无工作区快照）。"新写入特征行"是该文件本片段写入、且不在编辑前版本库版本里的行数（只算 ≥ 15 字符的行）；"去向"列出这些行进入了哪个提交、或此后没有提交覆盖它们。新写入特征行为 0 的文件（写的都是短行，或内容在版本库中已有）另列出写入内容原文，请与第 3.2 节该文件其后提交的 + 行逐字对照 |

| 第 3.1 节 含本片段新写入行的提交（逐文件覆盖比例、重合行样例、该提交还含哪些片段的内容） | 第 3.1 节 | 重合行直接列出，可逐行核对 |
| 第 3.2 节 其后改过同一文件的其他提交（不含 3.1 已列的） | 第 3.2 节（按时间推测的候选） | 覆盖 0% 的是**反面**证据：改了文件却不含本片段的特征行。覆盖高的多是同一内容先进入分支提交（已列在 3.1）、后随合并或压缩再次进入主线——这不是第二个去向，不据此填拆分。对新写入特征行为 0 的文件，这一节改列这些提交在该文件上的 + 行，由你与第 2.1 节的写入内容原文逐字核对：对得上 → 该提交含本片段的内容（按 A1/A2/A3 判）；对不上 → 不含 |
| 第 3.3 节 片段期间版本库中的提交 | 第 3.3 节 | 含提交者名字（公开信息），可看出是智能体还是人手工提交 |
| 第 3.4 节 其他会话在前后 48 小时内改过相同文件的片段 | 第 4 节（任务书） | **没有任务书**；这一节替代为跨会话线索，用于 A3 |

## 2 判定中的几条补充约定

1. **什么算代码**：与 v2.6 相同。`.md`、`.txt`、`.json`、`.yaml`、`.lock`、图片、日志不算；`docs/`、`.claude/`、`.entire/`、`specs/`、`plans/` 目录下的文件不算。证据包第 2.1 节已只列代码文件；只改非代码文件的片段不会进入样本。
2. **Edit 与 Write**：Claude Code 的 `Edit` / `MultiEdit` 是局部替换，"新写入行"= 写入内容 − 被替换内容 − 版本库旧行；`Write` 是**整文件重写**，"新写入行"只能减去版本库旧行，所以第 2.1 节里 Write 的"新写入行"可能包含**同会话此前片段写入、尚未提交、本片段只是原样重写**的行。遇到 Write 时请对照请求与上一片段：
   - 本片段自己新增或修改的内容与此前片段的内容进入同一提交 → 仍是 **A2**（成因多为 C2 或 C5）。
   - 第 3.1 节列出的提交里只有此前片段的行、本片段自己改的那部分并没有进入 → 按本片段自己内容的去向判（可能 A9 或 U），备注写"Write 重写继承"。
   - 看不出哪些行是本片段自己写的 → 填 U，缺什么写"Write 整文件重写，分不出本片段自己新增的行"。
3. **单独一条提交消息**：开发者说"commit"/"提交"而智能体没改代码的片段不是代码修改片段，不在样本中。但它的提交命令是**本片段**内容去向的证据（第 2.3 节）：该提交只含本片段的内容 → A1；还含同会话其他片段的内容 → A2；含其他会话的 → A3。"提交由后一条消息触发"本身不改变模式。
4. **A4 与 A5**：该语料没有任务书。只有当**请求本身**列举了多条事项、且第 3.1 节的多个提交按提交信息能一一对上这些事项时填 A4；其余多提交情形（同一件事分几次提交、补修复、先提交一部分后提交另一部分）填 A5。
5. **A6 随他项提交**：判据不变——提交信息指向与本片段请求**无关**的事。开源仓库的提交信息常是 `feat: …` / `fix: …`，请以其描述的功能与请求对照；对不上且不是同一功能的上下游时填 A6。
6. **A7 顺序压平**：该语料中"需求文件"对应 `.claude/plans/*.md`、`docs/*.md`、`specs/*.md` 等，它们不算代码、不在第 2.1 节；本片段若先写了这类文件再改代码并一起提交，第 3.3 节的提交改动文件数会体现。可凭请求与提交改动文件判 A7，置信度最高 2。
7. **压缩合并与变基（缺失 vs 无法确认）**：这些仓库的历史可能被改写：智能体回显的提交哈希在公开历史中找不到时，第 2.2 / 2.3 节会标"**回显哈希不在公开历史中**"。此时：
   - 第 3.1 节仍找到了含本片段行的提交（通常是并入主线的压缩提交） → 按该提交判，备注写"压缩合并"；多个片段被一个压缩提交收进去时是 A2 / A3，这正是要计数的现象，不是错误。
   - 第 3.1 节为空，而回显哈希找不到 → 填 **U**，缺什么写"历史被改写，回显提交不在公开历史中"；**不要填 A9**。
   - 第 3.1 节为空、没有回显哈希缺失、且第 3.2 节显示其后有提交改过这些文件却不含本片段的行 → **A9**（证据明确）。
   - 第 3.1 节为空、这些文件其后再无任何提交 → A9，置信度最高 2；若片段起点距镜像最后一次提交不足 48 小时（证据包首部给出两者时间），备注写"窗口末"。
8. **分支**：第 3.1–3.3 节的提交来自仓库全部分支（不含观测工具自建的 `entire/*` 分支）。内容进入了某个分支上的提交就算"进入版本库"，不要求并入主线。
9. **语言**：请求与提交信息多为英文，按原文理解即可；备注可用中文。
10. **成因**：C6"任务书流程"在此对应仓库的 `CLAUDE.md` 或请求中写明的"每步提交"规则（请求或会话消息摘要中能看到时才填）；C1 一般不适用；其余 C 代码照用；不贴切时 CX 并描述。
11. **置信度**：第 3.1 节重合行覆盖大部分新写入行、且前后消息一致 → 3；覆盖只有一部分，或要靠提交信息与请求对照 → 2；只有时间接近 → 1。
12. **短行与 N1**："新写入特征行为 0"不等于"无新增内容"。第 2.1 节列出的写入内容原文若表明本片段确实加了东西（例如在 `.dockerignore` 加一行 `backend/tests`），就按这些内容的去向判——与第 3.2 节其后提交的 + 行逐字对照，进入了就按 A1/A2/A3，没进入就 A9；只有写入内容在编辑前的版本库版本中已存在（恢复、格式化、原样重写）时才填 N1。
